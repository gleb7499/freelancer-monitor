# Freelancer.com — Правила отбора заказов (единый источник правды)

> Обновлено: 2026-10-21. Каналы заказов — feed и поиск, ставки — через закрытый
> веб-API (технические детали вынесены в `docs/freelancer-api.md`).
> Значения в таблицах вынесены так, чтобы их можно было менять одной правкой.
>
> **Приоритет правил:** явные требования заказчика в самом заказе (формат и
> содержание отклика, структура этапов, сроки, вопросы, на которые нужно
> ответить) выше любых общих правил этого файла и выполняются безоговорочно.
> Исключение — жёсткие НЕТ ниже (чужой стек, созвоны, оплата вне платформы,
> бесплатная работа, абьюзивный клиент): они решают, откликаться ли вообще.

## Все правила (кодовые фильтры — не переоценивать)

| Правило | Значение | Где применяется |
| --- | --- | --- |
| Язык заказа | английский; остальные — пас | Код |
| Явный фуллтайм | пас | Код (`upgrades.fulltime`) |
| Конкуренция (число откликов) | заказы с большим числом откликов отсекает код до скоринга (гейт фазы 0); LLM число откликов не передаётся вообще | Код |
| Оплата клиента | в данных заказа поле `client`: payment_verified/deposit_made/рейтинг/число открытых заказов. **Философия фазы 0 (решение Gleb'а): неверифицированная оплата, новый аккаунт, нет депозита, пустой `client` — НЕ минусы и НЕ основание для PASS.** Это ожидаемый фон подвала рынка: бидимся на всё, на что фрилансеры с отзывами не идут. Фиксируй эти факты в `check_manually` (для оператора — на будущее, при разговоре с клиентом просить milestone), но вердикт BID/PASS они не определяют | LLM-скоринг |
| Бесплатные тесты | запрещены — пас | LLM-скоринг |
| Дедлайн короче 7 дней при объёме более 30 ч | вердикт не меняет: запиши нюанс в `deadline_caveat` | LLM-скоринг |
| Пограничные / неясные случаи | при сомнении — BID; PASS только при явном НЕТ из списка ниже | LLM-скоринг |

> **Конкуренцию оценивает не LLM, а код.** Заказ берётся через секунды после
> публикации; если откликов уже много, такие заказы код отклоняет до скоринга
> (гейт фазы 0). LLM число откликов не передаётся: ранг определяется отзывами,
> milestone-историей и профилем, а не хронологией. Порогов и «придирчивости»
> от конкуренции нет.

## Что оценивает LLM — ТОЛЬКО два критерия

### 1. Бюджет через value-score

LLM оценивает **только** целесообразность цены. Механика:

1. Оцени `ai_hours` — часы работы с учётом того, что исполнитель работает с роем
   AI-агентов (быстро). **Упоминать AI-агентов / AI-ускорение в любом поле,
   читаемым клиентом, ЗАПРЕЩЕНО.**
2. **Сумму ставки устанавливает КОД, не ты** — детерминированное правило
   стратегии первых отзывов: ставка — ВСЕГДА низ вилки, без исключений
   (решение Gleb'а, фаза 0): бидимся на всё, на что нормальные фрилансеры
   с отзывами не пойдут. `bid_avg` не используется, в валюте заказа
   (fixed и hourly одинаково), круглая сетка. Поля `bid_amount`/`net_amount`
   заполняй любыми положительными числами в валюте заказа — код пересчитает
   сам.
3. `value_score = clamp(0..100, usd_rate / TARGET_HOURLY × 100)` — считает код
   в USD-пересчёте. **Низкая цена даёт низкий score — это ожидаемо и НЕ
   основание для PASS**, если стек подходит.

Пороги (код пересчитает score сам и принудительно сделает PASS, если score
ниже минимума):

- **< BID_MIN_SCORE (значение из конфигурации)** → PASS всегда.
- **>= BID_MIN_SCORE** → вердикт по стеку и рискам (см. раздел 2).

### Жёсткие НЕТ фазы 0 — ТОЛЬКО риск нечестного отзыва

Стратегия фазы 0: откликаемся на заказы, на которые фрилансеры с отзывами
не пойдут; цель — первые положительные отзывы. Поэтому всё «непривлекательное»
в клиенте (оплата не верифицирована, аккаунт свежий, ТЗ кривое, срочность,
мелкий бюджет, данных нет) — это НЕ причины для PASS, а наш рынок. Единственный
клиентский жёсткий стоп — признаки неадекватности, при которых даже хорошая
работа получит нечестный негатив:

- **абьюзивный или угрожающий тон описания** (капс, оскорбления, «no excuses»,
  угрозы негативом, ультиматумы) — PASS;
- **рейтинг работодателя < 3.5** при наличии отзывов — PASS (паттерн
  конфликтности);
- **условия, гарантирующие конфликт**: «unlimited revisions»/«правки до
  полного моего удовлетворения» в фикс, оплата только после безграничных
  правок, отказ от любой предоплаты при крупном скоупе — PASS;
- **вывод оплаты или общения вне платформы** (телефон/мессенджер/почта,
  оплата напрямую) — PASS (бан аккаунта + нет защиты отзывом);
- **бесплатная работа** («сделайте демо/тест, потом решу») — PASS
  (неоплаченная работа заканчивается спором).

Операционные стопы (не про клиента, не обсуждаются): чужой стек,
крипто/рекрутер (режет код до скоринга), созвоны, дизайн без кода.

### Срочность и кривизна ТЗ (фаза 0)

«ASAP»/«срочно», противоречивое или кривое ТЗ, расплывчатый скоуп, узкая ниша —
НЕ причины для PASS: на такие заказы нормальные фрилансеры с отзывами не идут,
это наш рынок. Отмечай нюансы в `check_manually`. Работает только в фазе 0: при
смене фазы пересмотреть.

### Апгрейды

Апгрейды ставки (sealed) покупает код сам после каждой успешной ставки.
LLM их не выбирает и не упоминает ни в одном поле.

### Политика этапных платежей (milestones)

Этапная оплата — ВСЕГДА, на любом fixed-заказе, без исключений. Причины:
так платформа считает ранг (оборот + частота релизов), а отзыв возможен
только при полной оплате через milestone-систему; досрочный релиз +
жалоба клиента штрафуют ранг.

План этапов (поле `milestones`) заполняешь ТЫ при скоринге — код его не
фиксирует, а только пересчитывает суммы от итоговой ставки:

- первый этап — ВСЕГДА 30% (предоплата перед стартом);
- число и доли остальных этапов выбираешь сам: 2–4 крупных ГЛОБАЛЬНЫХ
  этапа (уровень «Project setup» / «Core implementation» /
  «Final delivery and handover»), НЕ детальный план работ — точные границы
  выполнения на момент ставки неизвестны;
- описание этапа — английским, 10–250 символов (платформа проверяет и
  фронт, и сервер); доли целые, сумма строго 100;
- размер заказа значения не имеет: на fixed этапы планируются всегда, `null`
  не допускается (платформа явно рекомендует поэтапную оплату); hourly-проекты —
  всегда `null` (этапов нет);
- ИСКЛЮЧЕНИЕ АБСОЛЮТНОЕ (требование клиента выше наших типовых планов): если клиент САМ
  явно предложил структуру этапов в описании заказа (раздел «MILESTONE
  PAYMENTS», «платежи по этапам» и т.п.) — бери его структуру дословно:
  число этапов, доли и описания из его текста (переведи описание на
  английский, если клиент писал иначе; цели этапа не переиначивай).
  Наши типовые доли/описания не подставляй — клиент увидит несоответствие
  своему ТЗ и отклонит. Платформенная валидация требует первый этап ровно
  30%: если у клиента он другой — сохрани его число этапов и границы,
  минимально сдвинув доли так, чтобы первый стал 30%, сумма осталась 100
  и порядок этапов не изменился.

Все этапы создаются запросами СРАЗУ после ставки (POST milestone_requests —
заказчик видит структуру оплаты вместе с откликом, это фактор ранжирования);
дальнейший релиз — только по факту готовности: досрочный релиз + жалоба
клиента штрафуют ранг.

### 2. Стек

- **Ядро (брать уверенно):** React, Next.js, TypeScript, Spring Boot,
  PostgreSQL, Docker, HTML/CSS.
- **1–2 чужих, но известных элемента** (Python, FastAPI, Node.js, Express) —
  НЕ основание для PASS. Письмо пиши уверенно, без акцента на пробелах, без фраз
  вроде «я не знаю X».
- **Полностью чужой стек** — PASS: Flutter, React Native, .NET, Unity,
  WordPress (темы, плагины), CMS-конструкторы (Wix, Tilda и т.п.), дизайн-only,
  мобильная разработка (кроме заказов под профиль Android Development, если он
  есть в блоке профилей выше).
- **PHP — не чужой стек, если это доработка или интеграция**: правка вёрстки и
  фронта в существующем PHP-сайте, подключение React/JS-части, интеграция с API
  (в портфолио есть именно такой проект) — BID. PASS только если заказ целиком
  про PHP-разработку с нуля, WordPress-плагины или темы.
- **Shopify — НЕ знаем, всегда PASS** (решение Gleb'а, 12.10.2026): любые
  заказы вокруг платформы — темы и кастомизация на Liquid, приложения для
  Shopify, правки админки/чекаута, интеграции через Shopify API — пас НЕЗАВИСИМО
  от остального стека в описании и от доли «знакомых» слов. Shopify в названии
  или описании = заказ построен внутри чужой платформы, мы там не работаем.
  Единственное исключение — headless-коммерция: если клиент прямо просит
  Next.js/React storefront поверх Shopify Storefront API (Liquid не
  упоминается), это ядро стека — можно BID.
- **Cryptocurrency-проекты — всегда PASS**: категория требует верификации
  аккаунта Freelancer (Verified), наш аккаунт не верифицирован — API отклонит
  ставку с 403 RESTRICTED_FROM_BIDDING_PREMIUM_VERIFIED_JOB (проверено
  04.10.2026). Не трать цикл скоринга на них.
- **Recruiter-проекты (`upgrades.recruiter=true`, бейдж RECRUITER) — всегда
  PASS**: доступны только Preferred Freelancer, наш аккаунт не подходит
  (подтверждено скриншотом сайта 04.10.2026). Код режет такие ставки до POST.
- Чистый дизайн без кода (UI/UX, «design only») — PASS.
- **Заказы, где созвон обязателен для работы, — PASS**: само задание это
  консультация или звонок, обязательные регулярные созвоны/встречи, «intro call»
  как условие найма — у исполнителя нет ни времени, ни возможности для звонков.
  Мимолётное «happy to jump on a call if needed» в описании — НЕ повод для PASS.

### Контекст bids-ресурса

В user message код передаёт `bids_balance` и `next_bid_in_minutes`:

- Баланс 1–2 и долгий реген (более ~12 ч) — поднимай планку: value_score
  ниже ~20 → PASS. Ставка — на самые очевидные заказы.
- Баланс unknown — планку не меняй.

### Объём-ловушка

Дёшево ≠ мелко. Считай часы (opt/real/pess в поле `hours`). Не исключай
объёмные заказы только из-за цены — решение делает value-score.

### Материалы заказа (обязательны к анализу)

В JSON заказа приходит `artifacts` — распарсенные приложенные файлы и страницы
по ссылкам из описания (код скачивает и извлекает текст сам). Всегда учитывай
их содержимое при оценке часов и подводных камней: это часть требований
клиента, а не необязательное чтение. Плейсхолдер про бинарный файл (PDF/DOCX)
означает, что содержимое не извлечено — закладывай в оценку время на его
изучение при старте.
